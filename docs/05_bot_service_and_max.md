## 1. Роль и назначение Bot Service

**Bot Service** (порт 8001, `services/bot_service/main.py`) — это фронтенд-шлюз платформы в экосистеме мессенджера **MAX** (`@t569_hakaton_max_bot`).  
Сервис построен на базе асинхронного фреймворка `maxbot` (`Bot`, `Dispatcher`, `Message`, `Callback`) и выполняет роль адаптера между протоколом чата и внутренней событийно-ориентированной шиной.

### Зоны ответственности:
1. **Приём сообщений и коллбэков**: обработка текстового ввода и кликов по инлайн-кнопкам.
2. **Дедупликация входящего трафика (`idempotency.py`)**: защита от повторных доставок вебхуков MAX через Redis `SET NX`.
3. **Классификация намерений (`classify_intent`)**: разделение команд, учебных запросов, смолл-тока и неясных слов.
4. **Watchdog-таймеры (`watchdog.py`)**: удержание внимания ученика при долгих ответах LLM.
5. **Форматирование и разбиение сообщений**: конвертация формул в читаемый Unicode и нарезка текста на чанки до 4000 символов (`text_formatter.py`).
6. **Двухрежимная шина**: штатная работа через топик Kafka `education.events` + прозрачный HTTP REST-fallback.

```
       [ Ученик в мессенджере MAX ]
                     │
                     ▼
         ┌───────────────────────┐
         │      Bot Service      │
         └───────────┬───────────┘
                     │
          1. Проверка дубликата (Redis SET NX)
          2. Классификация интента (command / educational / chitchat / vague)
          3. Запуск Watchdog (45 сек)
                     │
        ┌────────────┴────────────┐
        │ Штатный режим           │ Резервный режим (Kafka Down)
        ▼                         ▼
 ┌─────────────┐            ┌─────────────┐
 │ Apache Kafka│            │  Core / ML  │ (Direct HTTP REST)
 └─────────────┘            └─────────────┘
```

> 🔍 **Исходный код и функции шлюза**: Построчный разбор модулей бота (`main.py`, `idempotency.py`, `watchdog.py`, `keyboards.py`) см. в [Справочнике кодовой базы: Bot Service](./codebase_reference.md#sec-4).

## 2. Классификатор намерений пользователя (`classify_intent`)

Школьники пишут в мессенджер неструктурированный текст: от точных вопросов до смайликов и приветствий. Функция `classify_intent(text)` разделяет входящие сообщения на 4 категории:

```python
def classify_intent(text: str) -> str:
    # 1. Системные команды (/start, /reset, /help)
    if text.startswith("/"):
        return "command"

    # 2. Неясные / слишком короткие запросы (одиночные слова "уравнение", "закон")
    if lower in single_vague_words or (len(words) == 1 and len(text) < 4):
        return "vague"

    # 3. Разговорный оффтоп / chitchat ("привет", "как дела", "кто ты", "погода")
    if any(k in lower for k in chitchat) and len(words) <= 4:
        return "chitchat"

    # 4. Академические запросы (математика, физика, химия, биология, CS)
    if any(k in lower for k in school_keywords) or len(words) >= 2:
        return "educational"
```

### Поведение бота по категориям:
* **`command`**: Вызов соответствующих обработчиков (инициализация профиля, сброс состояния FSM, показ справки).
* **`vague`**: Бот не тратит токены LLM на бессмысленный запрос, а отправляет подсказку:  
  *«Кажется, вопрос слишком короткий ✍️ Напиши подробнее, какую именно тему или формулу разобрать (например: "Объясни закон Ома")»*.
* **`chitchat`**: Дружелюбный ответ с мягким дидактическим возвратом в контекст учебы:  
  *«Привет! Я твой виртуальный репетитор. Какую тему сегодня разберём?»*.
* **`educational`**: Запуск конвейера генерации метафоры и квиза.

## 3. Идемпотентность и дедупликация сообщений (`idempotency.py`)

Платформы мобильных мессенджеров работают по семантике **At-Least-Once Delivery**: если сервер бота не ответил кодом 200 за 2–3 секунды, платформа повторно отправляет тот же вебхук.  
**Риск**: Ученик получит 2–3 одинаковых длинных объяснения, а сервер потратит тройной бюджет токенов.

### Инженерное решение на базе Redis:
```python
async def is_duplicate_message(message_id: Optional[str], user_id: str, text: str) -> bool:
    now = time.time()

    if message_id:
        key = f"ingress_msg:{message_id}"
        ttl = 3600  # Храним ID сообщения 1 час
    else:
        # Синтетический хеш от пользователя, текста и текущей секунды
        sec = int(now)
        hash_val = hashlib.sha256(f"{user_id}_{text}_{sec}".encode("utf-8")).hexdigest()[:16]
        key = f"ingress_msg:{hash_val}"
        ttl = 60

    client = await get_redis_client()
    if client:
        # Атомарный SET NX: возвращает True ТОЛЬКО если ключа ещё не было
        is_new = await client.set(key, "1", ex=ttl, nx=True)
        return not bool(is_new)

    # In-memory fallback при недоступности Redis
    if key in _local_cache:
        return True
    _local_cache[key] = now + ttl
    return False
```

* Команда `SET key "1" EX ttl NX` атомарна и выполняется за < 1 мс.
* При повторном вебхуке `is_new == None`, функция возвращает `True` (дубликат), и обработчик мгновенно отсекает запрос.

## 4. Watchdog-таймеры («Таймеры спокойствия», `watchdog.py`)

Глубокий RAG-поиск по страницам учебника и инференс LLM могут занимать от 3 до 8 секунд.  
Если подросток отправил вопрос и не видит ответа более 10–15 секунд, он начинает нажимать кнопки повторно или считает, что бот завис.

### Архитектура Watchdog:
1. В момент отправки запроса в очередь регистрируется таймер на **45 секунд**:
   * Создается локальный `asyncio.Task`, засыпающий на `timeout_sec`.
   * Состояние дублируется в Redis: `SET active_watchdog:{correlation_id} {user_id} EX 45`.
2. **Сценарий А (Штатный)**:  
   Ответ `explanation.ready` пришел из Kafka за 3.2 сек.  
   Бот вызывает `cancel_watchdog(correlation_id)`. Фоновая задача отменяется через `task.cancel()`, ключ из Redis удаляется. Никаких лишних сообщений не шлется.
3. **Сценарий Б (Задержка внешней LLM / очередь)**:  
   Время ожидания превысило порог. Таймер просыпается и отправляет ученику сообщение:  
   *«⏳ Генерация подробного объяснения и квиза требует чуть больше времени. Пожалуйста, подожди ещё несколько секунд, ответ уже формируется! 🧠»*.

```
[ Запрос отправлен ] ──► register_watchdog(corr_id, 45s)
          │
    (Идет RAG + LLM)
          │
 ┌────────┴───────────────────────────┐
 │ Ответ готов < 45 сек               │ Задержка > 45 сек
 ▼                                    ▼
cancel_watchdog(corr_id)             Watchdog отправляет:
(Тишина, отправка ответа)             "Подожди ещё несколько секунд..."
```

## 5. Инлайн-клавиатуры и диалоговый UI (`keyboards.py`)

Для исключения ручного ввода и ошибок со стороны ребенка весь диалог построен на удобных инлайн-кнопках:

| Клавиатура | Назначение | Варианты выбора |
| :--- | :--- | :--- |
| **`get_consent_keyboard()`** | Комплаенс 152-ФЗ при старте | `✅ Да, я согласен` (полный профиль)<br>`🔒 Нет, гостевой режим` (обезличенно) |
| **`get_interests_keyboard()`** | Персонализация метафор | `⚽ Футбол` · `🎮 Видеоигры`<br>`🎵 Музыка` · `🚀 Космос`<br>`🎬 Кино` · `💡 Общий` |
| **`get_quiz_keyboard()`** | Закрепление материала | 4 кнопки вариантов ответа с коллбэком вида `quiz:{quiz_id}:{index}` |
| **`get_after_explanation_keyboard()`** | Развитие диалога после ответа | `🔄 Другая метафора`<br>`💡 Сменить увлечение`<br>`📚 Другая тема` |
| **`get_profile_keyboard()`** | Управление аккаунтом | `🔄 Сменить хобби`<br>`🗑️ Сбросить всё (/reset)` |

## 6. Отказоустойчивая доставка и сплиттер сообщений

### 1. Повторные попытки отправки (`send_message_with_retry`):
Если в момент отправки ответа возник сетевой сбой API мессенджера (например, таймаут шлюза), бот выполняет до 3 попыток с экспоненциальным бэкоффом:
$$T_{\text{delay}} = 0.5 \times 2^{\text{attempt}} \quad (0.5\,\text{с} \to 1.0\,\text{с} \to 2.0\,\text{с})$$

### 2. Сплиттер длинных ответов (`split_for_max`):
Лимит одного сообщения в MAX составляет 4000 символов. Если развернутое объяснение с квизом превышает лимит, алгоритм аккуратно нарезает его:
1. По границам абзацев (`\n\n`).
2. По границам строк (`\n`).
3. По границам предложений (`. `).  
Слова никогда не разрезаются пополам, а формулы и код сохраняют целостность.
