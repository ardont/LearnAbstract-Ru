## 1. Роль и назначение Core Service

**Core Service** (порт 8000, `services/core_service/main.py`) — это центральный «мозг» и координатор всей платформы.  
Он выполняет роль **BFF (Backend-for-Frontend)**, оркестрирует бизнес-логику, изолирует состояние пользователей и гарантирует отказоустойчивость всей системы.

### Ключевые зоны ответственности:
1. **Конечный автомат (FSM)**: Управление жизненным циклом сессии ученика и обеспечение комплаенса с **152-ФЗ**.
2. **Quiz Freshness Guard**: Защита от повторных нажатий старых кнопок и атак на FSM.
3. **Sliding Window Rate Limiter**: Защита от спама и DoS-атак на скользящем окне в 10 запросов в минуту (RPM).
4. **Управление базой данных**: Персистентность через PostgreSQL с прозрачным fallback на SQLite.
5. **Кабинет Учителя (`/teacher`)**: Серверный рендеринг SVG-аналитики и экспорт отчетов в Excel-совместимый CSV с кодировкой UTF-8 BOM.
6. **RAG Ingestion**: Прием и диспетчеризация загрузки PDF-учебников для индексации.

> 🔍 **Исходный код и сигнатуры**: Детальный разбор каждой функции (`fsm.py`, `rate_limiter.py`, `database.py`, `models.py`, `main.py`) см. в [Справочнике кодовой базы: Core Service](./codebase_reference.md#sec-2).

## 2. Конечный автомат ученика (FSM) и 152-ФЗ (`fsm.py`)

Для каждого ученика поддерживается строгое состояние в базе данных (`User.state`):

```
                  ┌─────────────────┐
                  │  GUEST_CHOICE   │ ◄── Первичный вход (/start)
                  └────────┬────────┘
                           │ Выбор согласия 152-ФЗ
           ┌───────────────┴───────────────┐
           ▼                               ▼
    [ Согласен: true ]             [ Согласен: false ]
    (полный профиль)               (is_guest = true)
           │                               │
           └───────────────┬───────────────┘
                           ▼
                  ┌─────────────────┐
                  │ SELECT_INTEREST │ ◄── Выбор хобби (Футбол, Видеоигры...)
                  └────────┬────────┘
                           │ Интерес зафиксирован в БД
                           ▼
                  ┌─────────────────┐
     ┌──────────► │      IDLE       │ ◄── Готов к приему учебных вопросов
     │            └────────┬────────┘
     │                     │ Ученик задал вопрос ("Объясни формулу")
     │                     ▼
     │            ┌─────────────────┐
     │            │   EXPLAINING    │ ◄── Запрос передан в Kafka / ML
     │            └────────┬────────┘
     │                     │ Сгенерирован ответ с микро-тестом
     │                     ▼
     │            ┌─────────────────┐
     └─────────── │   QUIZ_ACTIVE   │ ◄── Активен тест (current_quiz_id != None)
  Правильный      └─────────────────┘
  или неверный ответ
```

### Защита персональных данных (152-ФЗ):
* При первом входе FSM принудительно переводит пользователя в `GUEST_CHOICE`. Никакие учебные вопросы не принимаются, пока пользователь не сделает выбор.
* Если ученик нажимает **«Отказ (Гостевой режим)»**:
  * Выставляется флаг `is_guest = True`.
  * Внешние идентификаторы не связываются с личными данными.
  * В Kafka и во внешние нейросети (LLM) передается **исключительно обезличенный текст вопроса**, исключая утечку данных несовершеннолетних.

## 3. Quiz Freshness Guard: защита от атак на FSM

В интерфейсах мессенджеров (MAX, Telegram) пользователь может проскроллить историю чата вверх и нажать на кнопку квиза, пройденного 10 минут назад.

### Проблема без защиты:
1. Повторный клик может сбить текущее состояние FSM ученика (например, он сейчас ждет новое объяснение, а клик возвращает его в квиз).
2. Ученик может многократно кликать по правильному ответу, бесконечно накручивая себе баллы (XP).

### Инженерное решение в `verify_quiz_answer()`:
```python
# Проверяем пользователя
user = await session.execute(select(User).where(User.max_user_id == str(max_user_id)))

# КЛЮЧЕВАЯ ПРОВЕРКА FRESHNESS GUARD:
if not user or user.current_quiz_id != quiz_id:
    logger.warning(f"Quiz Freshness Guard сработал: активный={user.current_quiz_id}, прислан={quiz_id}")
    return {
        "status": "stale",
        "is_correct": False,
        "message": "⚠️ Этот тест уже не активен или был пройден ранее. Вопрос не засчитан."
    }
```
* Если `current_quiz_id != quiz_id` — система возвращает статус `"stale"`.
* FSM не ломается, очки не накручиваются, ученик получает понятное уведомление.

## 4. Скользящий Rate Limiter на Redis Sorted Sets (`rate_limiter.py`)

Для предотвращения DoS-атак и защиты бюджета LLM-токенов в `Core Service` реализован алгоритм **Sliding Window Log**:

* **Лимит**: 10 запросов в минуту (RPM) на пользователя.
* **Структура в Redis**: `Sorted Set (ZSET)` по ключу `rate_limit:{user_id}`.
* **Score и Member**: текущий Unix Timestamp (`time.time()`).

```python
pipe = client.pipeline()
# 1. Удаляем из множества все запросы старше 60 секунд
pipe.zremrangebyscore(key, 0, window_start)
# 2. Считаем, сколько запросов осталось в текущем 60-секундном окне
pipe.zcard(key)
# 3. Добавляем временную метку текущего запроса
pipe.zadd(key, {str(now): now})
pipe.expire(key, 65) # Автоматическая сборка мусора
results = await pipe.execute()

current_count = results[1]
if current_count >= limit_rpm:
    # Вычисляем точное время до разблокировки
    oldest = await client.zrange(key, 0, 0, withscores=True)
    retry_after = int(60 - (now - oldest[0][1]))
    return True, max(1, retry_after)
```

### In-Memory Fallback:
Если Redis временно упал, Rate Limiter **не блокирует пользователей**, а мгновенно переключается на локальный `collections.deque` с потокобезопасным `asyncio.Lock()`.

## 5. Кабинет Учителя (`/teacher`) и экспорт в Excel

Кабинет педагога спроектирован так, чтобы работать **полностью автономно в изолированных школьных сетях**:

1. **HTTP Basic Auth**: Аутентификация учителей с защитой от тайминг-атак через `secrets.compare_digest()`.
2. **Векторный SVG-график активности**: График активности класса за неделю генерируется бэкендом на лету в чистом SVG. Никаких внешних JavaScript CDN, Chart.js или запросов во внешнюю сеть — работает даже без интернета!
3. **Quiz Heatmap (Тепловая карта)**: Бэкенд делает выборку по таблице `quiz_sessions` и вычисляет темы с наивысшим процентом ошибок:
   $$\text{Error Rate} = \frac{\text{Неверные ответы}}{\text{Всего ответов}} \times 100\%$$
   Учитель сразу видит проблемные разделы (например, «Квадратные уравнения» или «Закон Ома»).
4. **Экспорт в CSV (`/api/teacher/export_csv`)**:  
   *Файл отдается со специальным байтовым префиксом **UTF-8 BOM (`\ufeff`)**:*
   ```python
   csv_buffer.write("\ufeff") # Предотвращает кракозябры в русском Excel
   ```
   Благодаря этому файл сразу открывается в российском Microsoft Excel с идеальными колонками и русскими символами.

## 6. Мониторинг здоровья (`GET /health/full`)

Для второго экрана демонстрации перед жюри в `Core Service` реализован эндпоинт `/health/full`:
* Статус PostgreSQL: `ok (postgres)` или `ok (sqlite_fallback)`.
* Статус Redis: `ok (redis)` или `degraded (in-memory fallback)`.
* Состояние брокера Kafka: `ready`.
* Метрики RAG: общее число запросов, RAG hits, RAG hit rate %, количество чанков.
* Системный Uptime и лог последних 10 перехваченных ошибок приложения (`LAST_ERRORS`).
